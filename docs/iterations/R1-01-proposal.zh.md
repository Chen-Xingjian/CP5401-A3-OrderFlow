# OrderFlow R1 需求验收稿

候选版本 **R1-01** · 2026-11-17 · **待学生验收**

校园文印店的客户想知道订单处理到哪一步、现在能否取件。工作人员需要看到待处理的订单，并在接单、开始制作、备好和交付时更新进度。客户和工作人员看到的当前状态应当能用同一份处理历史解释。

本轮请审阅 V1.0 要解决的问题、角色权限及每项要求的通过条件。确认后，这份需求作为 R2 开发依据。软件 Release V1.0 在后续完成实现、测试、部署和人工检查后建立。本文列出的结果均为**预期**，应用执行状态为 `NOT_RUN`。

## 1　功能需求及通过条件

| ID | 谁需要做什么 | 以后验收时应看到什么 |
|---|---|---|
| FR-01 | 客户创建订单 | 客户 A 选择一项开放服务，填写有效数量并提交。保存成功后得到唯一订单号，归属于 A，状态为「待确认」，历史中有一条创建记录。 |
| FR-02 | 客户查询自己的订单 | A 能从自己的列表打开详情，看到服务、数量、备注、当前状态和历史。客户 B 的列表没有这张单，使用同一订单号查询也取不到它的内容。 |
| FR-03 | 工作人员查看工作队列 | 以工作人员身份能找到 A 和 B 的订单、区分当前阶段并查看各单历史。普通客户只拥有客户视图及相应操作权限。 |
| FR-04 | 工作人员推进处理 | 接单、开始处理、处理完毕、实际交付分别推进一阶段。客户刷新后看到新状态。工作人员尝试把「已确认」直接改成「已完成」时，系统拒绝，订单和历史维持操作前的值。 |
| FR-05 | 有权查看订单的人回看处理历史 | 每条记录包含操作者、时间、原状态和新状态，按发生的业务顺序排列。走完四次推进后共五条，首条是创建，末条是交付；此时订单显示「已完成」。 |

## 2　业务规则

| 对应编号 | V1.0 规则 |
|---|---|
| BR-01、BR-04 | 客户用预设账户登录，下单时系统从登录身份取得所有者。客户能创建和查看自己的订单。工作人员能查看全店订单并推进流程。服务层对每次读取和写入核对身份与权限。 |
| BR-02 | 每单选择一个当前开放的目录服务，数量按该服务的份数计，取 1–99 的整数。备注可空，最多 500 字符。服务无效、数量越界或备注超长时提示更正，产生零张新订单。 |
| BR-03、BR-11 | 工作人员依次执行「待确认 → 已确认 → 处理中 → 待领取 → 已完成」。待领取表示制作完毕、客户可以取件。实际交付后工作人员才能确认完成。已完成是终态。 |
| BR-05、BR-06、BR-07、BR-12 | 创建时订单版本为 0，首条历史序号为 0。每次成功推进，状态与历史在同一事务中保存，版本加 1，历史增加一条。历史按序号排列，最后一条的目标状态等于当前状态。 |
| BR-08、BR-09 | 推进时核对工作人员打开页面时看到的版本。若订单已被其他会话更新，提示刷新。所有遭拒或写入失败的操作都保留已提交的状态、版本和历史。 |

范围沿用设计中的预置服务目录、店内处理及领取。支付、库存、配送、上传打印原件和订单编辑均在本次范围之外。**FR-06、BR-10 属于后续候选变更 CR001。** 拟在 V1.0 发布后提出「客户在待确认或已确认阶段取消本人的订单」，届时再审批具体权限和异常规则。

## 3　软件质量要求

| ID | 质量要求与可测标准 | 后续如何取得证据 |
|---|---|---|
| QR-01 | **记录可靠。** 写入中途失败并回滚后，另一连接读取的状态、版本、历史与操作前完全一致。成功提交后，关闭会话并重新读取，记录仍在。 | 数据库集成测试 T15、T16、T19；发布时以真实部署重开会话复核。 |
| QR-02 | **订单保密。** B 对 A 的订单可见条数为 0。无权限或身份失效时，详情、历史和错误信息均不透露订单内容。客户不能执行工作人员操作。 | 两个客户和一个工作人员的服务层测试 T04–T08、T12，以及界面和错误信息检查。 |
| QR-03 | **竞争更新只生效一次。** 两个工作人员会话对同一版本各提交一次合法推进，数据库正常时恰好一次成功。另一次收到刷新提示，版本和历史总计各增加 1。 | T17 使用两条独立数据库连接；检查双方结果及最终记录。 |
| QR-04 | **质量检查可复现。** 同一提交在本地和 GitHub Actions 使用相同测试入口、固定演示数据和隔离测试库。已知测试失败时检查应失败，能从运行记录定位到提交和测试。 | 对照本地命令、PR 运行日志、测试报告及提交标识。 |
| QR-05 | **用户能判断下一步。** 客户能独立找到自己的订单，正确解释「处理中」还需等待、「待领取」可以取件。工作人员能说出下一步并完成对应操作。 | VAL-01 任务观察。记录是否完成、是否需要主持人提示及具体误解；需要提示或判断错误的任务记为待改进。 |

## 4　端到端验收场景

计划使用虚构的客户 A、客户 B、工作人员 S，以及开放服务「黑白打印」。T 编号沿用[测试计划](../test-plan.md)。下表也列出人工需要直接观察的结果。

| ID | 条件和操作 | 通过标准 | 对应证据 |
|---|---|---|---|
| AC-01 | A 创建 2 份黑白打印订单，备注为空。 | 获得一个订单号；重新打开仍属于 A，数量 2、状态待确认、版本 0，恰有一条 A 创建的历史。 | FR-01、FR-05、QR-01 / T01、T09、T19 |
| AC-02 | 分别试数量 1、99、0、100、1.5；试用空备注、500 字符、501 字符，以及已停用服务。每次只改变一项输入。 | 1 和 99 合法；0、100、1.5 拒绝。空备注和恰好 500 字符合法；501 字符与停用服务均拒绝。每次拒绝后订单与历史新增数均为 0。 | FR-01、BR-02 / T02–T03，拒绝写入以集成检查核对 |
| AC-03 | A、B 各有一单。分别用 B 和 S 查看列表，再查询 A 的详情及历史。 | B 仅看到自己的订单，查询 A 的单返回通用无可访问记录提示。S 可看到两单及各自历史。 | FR-02、FR-03、QR-02 / T05–T08、T20 |
| AC-04 | S 将新订单逐步处理至制作完毕，再确认交付。 | 制作完毕时 A 看到待领取。交付后 A 看到已完成、版本 4；五条历史依次对应创建及四次推进，操作者依次为 A、S、S、S、S。 | FR-04、FR-05 / T09–T10、T20 |
| AC-05 | 用当前版本分别尝试跳步、倒退、继续推进已完成的订单，以及让客户推进自己的订单。 | 非法状态转换或无权限操作得到拒绝。用新连接复核，状态、版本、历史均与尝试前相同。 | FR-04、QR-01、QR-02 / T11–T13 |
| AC-06 | 系统准备把已确认订单改为处理中，在状态写入与历史提交之间模拟存储故障。 | 用户看到操作未完成；重读仍为已确认，版本和历史均没有增长。 | BR-05、QR-01 / T15–T16 |
| AC-07 | 两个工作人员会话都读到某订单已确认、版本 1，并提交开始处理。 | 一方成功，另一方得到版本冲突提示；重读为处理中、版本 2，共三条历史。 | BR-08、QR-03 / T14、T17 |
| AC-08 | 在同一候选提交上执行本地及 PR 测试；用户随后在运行中的应用完成下单、查询及取件判断任务。 | 测试结果可定位到提交；另行记录用户的操作、解释和提示需求，按 QR-05 的条件判断任务是否达成。 | QR-04、QR-05 / CI 运行记录、VAL-01 |

## 5　风险与本轮决定

两项优先风险是客户看到他人的订单，以及工作人员看到的进度与历史不符。前者由服务层按身份限定读取范围并用 AC-03 检查；后者由事务和版本校验控制，用 AC-06、AC-07 检查故障与竞争。AI 起草需求和后续测试时，预期结果以你认可的业务规则为准。

**请你判断**：一单一项服务、1–99 份和 500 字备注是否符合演示场景；「待领取」和「已完成」是否准确区分制作与交付；取消功能是否适合留作后续变更；上述成功与失败结果是否足以让你判断产品符合需求。可直接指出要改的 FR、BR、QR 或 AC 编号。
