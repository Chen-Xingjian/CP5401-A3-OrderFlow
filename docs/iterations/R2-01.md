你可以实际创建一张文印订单，查看另一位客户能看到哪些数据，让工作人员逐步推进订单，再观察跳步、旧请求及数据库故障后的订单和历史。业务代码、数据库、测试、英文提示、README 和 GitHub Actions 均使用英文。历史 R1 验收稿与本轮验收单保留中文。

| 你要判断的规则 | 实际观察与证据 |
|---|---|
| 创建与归属 | 客户 A 下单后得到独立 UUID，状态为 PENDING、版本 0，第一条事件来自 A。客户 B 的列表没有该单。查 A 的订单和查一个不存在的订单，B 得到相同提示。 |
| 数量、备注与目录 | 1、99 份及空备注、500 字符备注均可保存。0、100、1.5、布尔数量、501 字符备注及停用项目被拒。拒绝创建后，两张表的新增行数均为 0。 |
| 制作与交付 | PENDING → CONFIRMED → PROCESSING → READY_FOR_PICKUP → COMPLETED。制作完毕是 READY_FOR_PICKUP，实际交付后才确认 COMPLETED。四次推进后版本为 4、历史共 5 条。 |
| 写入中途失败 | 从 CONFIRMED、版本 1 开始，在插入历史前和提交时分别触发真实数据库异常。另开连接重读，仍为 CONFIRMED、版本 1、两条历史。新订单创建时也检验了这两处失败。 |
| 两人同时处理 | 两个工作人员读到同一版本 1，然后同时提交 PROCESSING。正式检查中 staff-t 成功，staff-s 收到 STALE_VERSION。重读为 PROCESSING、版本 2、三条历史。重跑时成功者可以不同。 |

## 5. 本轮数据库评估补充

A3 第 2–3 页要求通过小应用展示质量工程、正确管理信息并部署可访问的应用。第 10–12 页的 HD 标准考查可靠行为、验收标准、规则、边界、失败测试和可信过程证据。数据库产品由项目自行选择。PostgreSQL 是我们当前架构方案中的选择，SQLite 也能支撑本项目规模的订单业务。

| 取舍 | SQLite | PostgreSQL |
|---|---|---|
| 准备和运行 | Python 附带驱动，主要管理一个本地文件，适合减少环境准备 | 需要数据库进程或托管服务及连接配置 |
| 下单、历史及回滚 | 能用事务保证订单与历史一同提交 | 当前候选已实际验证同样合同 |
| 两位工作人员更新 | 可通过短事务、等待及版本校验保证一次成功、另一方刷新 | 当前使用订单行锁与版本校验，有真实竞争结果 |
| 部署后数据保留 | 本地或有持久磁盘的单实例可行；Community Cloud 的本地文件保留需要另行解决 | 外部数据库独立于应用文件系统，部署时核验保留与连接行为 |
| 对本轮的影响 | 要调整 SQL、事务控制、测试隔离和故障注入，然后重新验收 | 可继续使用本轮已实现并验证的版本 |

SQLite 官方说明其适合应用本地存储及许多小型网站，并提供事务。其一个时刻的写事务数为一，因此本项目采用 SQLite 时需要为第二次写入设置等待或有限重试，并重新核对版本。订单量和两种用户角色足以使用这个方案。[SQLite 使用场景](https://www.sqlite.org/whentouse.html)、[SQLite 事务](https://www.sqlite.org/lang_transaction.html)

影响当前建议的是 Community Cloud 的存储条件。Streamlit 官方明确表示该平台的本地文件持久性没有保证，因此本地 SQLite 文件需要额外的可靠保存方案。[Streamlit 数据连接说明](https://docs.streamlit.io/develop/concepts/connections/connecting-to-data)

**按目前的 Streamlit Community Cloud 部署方向，建议保留单个外部 PostgreSQL。** 若目标改为本地演示或有可靠持久磁盘的单实例部署，SQLite 是更轻量的选择。两种方案都能形成 HD 所需的质量证据，评分依据取决于业务、验证和过程证据。选择 SQLite 后，可在 R2 内完成存储调整并交付新的候选验收。

当前代码用到了 PostgreSQL 的行锁、枚举、时间函数、schema 隔离及故障触发器，切换 SQLite 会涉及这些实现与对应测试。英文 [数据库评估](../database-choice.md)记录了官方依据和文件影响范围。本次交付补充文档，R2-01 的业务源码指纹沿用原记录。
