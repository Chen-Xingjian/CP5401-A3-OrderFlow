### Upgrade experiment

1. Initialise a temporary SQLite file through the V1.0 entry point and its two migration files from the release tag. Create one pending order.
2. At the same app path, load the candidate entry point and restore the candidate migration directory. Retain the Streamlit resource cache and interpreter.
3. Select Cancel order. Only migrations 001 and 002 remain installed. The UI reports a persistence error and the original order is still pending.
4. As a control, clear the resource cache and load the candidate on the same database. Migration 003 now appears and cancellation succeeds with two events.

This experiment establishes the same-process failure. A host starting a fresh process takes the cold-start path. The public V1.0 application was not used for these experiments.

## Other risk checks

- **Ownership and retries.** The service checks the active role, scopes the order lookup to its owner, then checks the displayed version before the state. T23 and T24 cover inaccessible orders, repeat cancellation and stale submissions.
- **Concurrent writes.** BEGIN IMMEDIATE reserves the SQLite writer before status/version reads. T25 checks the final event and actor after a customer cancellation races a staff production update.
- **Atomic writes.** Order and history share a transaction. T26 injects a failure during history insertion and a deferred failure at commit; each preserves the previous snapshot.
- **Scope and regression.** The workflow and the two V1.0 migration files match the baseline. The full local suite passed 120 cases during review. [Implementation CI](https://github.com/Chen-Xingjian/CP5401-OrderFlow/actions/runs/45009325053) also passed. The R6 student observations cover customer visibility, the production cutoff and the terminal staff view.
